# ESP32-S3 + RC522：Wi-Fi 网页识别和 M1 卡数据备份

开机自动建立 Wi-Fi 热点，手机连接后即可在中文网页完成卡片识别、备份、恢复、校验和 JSON 下载；也保留原有串口命令。适用于你有权读取、备份的卡片。

## 手机快速使用

1. 在 Arduino IDE 中打开本目录的 `CardBackup/CardBackup.ino`，将同文件夹内所有 `.h`、`.cpp` 文件一起保留，重新上传。
2. **升级保持原来的分区设置，并让 `Erase All Flash Before Sketch Upload` 保持 Disabled。** 本版沿用原来的 NVS 格式和存储位置，可直接使用原先保存在板上的备份。你已验证可用的原生 USB 设置是 `USB CDC On Boot = Enabled`、`USB Mode = Hardware CDC and JTAG`。
3. 上传后按一下 RST，等待几秒。用手机连接热点 **`ICCard-S3`**，密码 **`iccard2026`**。
4. 在手机浏览器地址栏完整输入 **`http://192.168.4.1`**（HTTP）。部分手机会自动弹出页面；如果没有弹出，手动打开即可。
5. 若手机提示“此 Wi-Fi 无互联网”，选择继续连接/仍然使用。页面不需要互联网。日常使用可以接 USB 充电器或移动电源供电，无需电脑。

| 网页按钮 | 操作 |
| --- | --- |
| 识别卡片 | 放一张卡，读取 UID 与类型 |
| 备份原卡 | 放原卡，将全部用户数据读取后保存；有旧备份时先弹出替换提示 |
| 检查目标卡 | 移走原卡、放空白卡，先检查全部扇区；此时尚未写卡 |
| 确认写入这张卡 | 核对页面上的目标 UID，在 30 秒倒计时内点击；不必输入串口命令 |
| 校验目标卡 | 比较目标卡和板上备份的 47 个用户数据块 |
| 下载备份到手机 | 保存用户数据 JSON，文件名包含原卡 UID |
| 第 0 块写入方式 | 自动选择、仅 UID / Gen1A、仅 CUID / Gen2 标准认证三种选项 |
| 检查第 0 块写入 | 只检查和读取，显示本次待尝试的写入方式，不写入 |
| 确认写入第 0 块 | 单独复制备份中的完整第 0 块，写后重新识别 UID 并回读 16 字节 |
| 确认标准写入第 0 块 | 普通认证后实际尝试一次写入；准备通过并不保证第 0 块可写 |
| 更多操作 → 删除板上备份 | 再次确认后删除板上数据 |

页面会自动刷新读卡器状态、备份信息、最近识别的卡号和当前操作进度。最近识别的卡号是历史结果，不代表该卡此刻仍在天线上；实际写入前还会重新选卡并核对 UID。等待确认时可点击“取消”。读写进行中，其他操作会禁用，重复提交也会在设备端被拒绝。

修改热点名称/密码可编辑 [Config.h](CardBackup/Config.h) 中的 `WIFI_AP_SSID`、`WIFI_AP_PASSWORD`，密码需要 8～63 个字符，然后重新烧录。接入热点即可使用本机页面，不另设网页账户。页面的脚本、样式和图标全部存放在板上，不依赖外部网站。

若热点不显示，查看串口启动输出是否有 `Wi-Fi hotspot:`。若显示热点但打不开页面，确认手机仍连接此热点，地址以 `http://` 开头；可临时关闭 VPN 或手机自动切换移动数据的功能。在自动弹出的网络登录小窗口中无法下载文件时，请用 Safari / Chrome 打开同一地址再下载。

普通备份/恢复处理 MIFARE Classic 1K（M1 / S50）的 47 个用户数据块；另有独立的 **UID / Gen1A 和 CUID 标准认证第 0 块写入**流程，可写入兼容目标卡的 UID 与厂家信息。普通 M1 卡的第 0 块出厂只读。程序不复制扇区密钥或访问控制位，也不恢复未知密钥，因此即使卡号和用户数据一致，也不保证所有设备会接受新卡。

## 复制卡号与第 0 块（UID / CUID）

本功能限定 **4 字节 UID、S50 / MIFARE Classic 1K**。可以自动选择待尝试的写法，也可以手动选 UID / Gen1A 或 CUID / Gen2。默认目标 Key A 为 `FFFFFFFFFFFF`；标准认证方式还要求目标第 0 扇区为本程序支持的出厂访问位 `FF0780`。

| 写入方式 | 确认之前的检查 | 确认之后 |
| --- | --- | --- |
| 自动选择 | 先检查 Gen1A 握手，并读取、比对第 0 块；未通过时重启 RF 场，重新识别同一张卡，做普通认证、读取和访问位检查 | 只使用页面实际显示、且你已确认的那一种写法 |
| 仅 UID / Gen1A | 检查现有库的 Gen1A 握手，并回读完整第 0 块比对 | 重新核对目标，使用同一 Gen1A 方式写入一次 |
| 仅 CUID / Gen2 | 普通 Key A 认证、读取第 0 块、检查访问位；不会发送特殊唤醒命令 | 保持普通认证会话，尝试一次标准第 0 块写入 |

**自动选择的是待尝试的写法，不能无损鉴定确切卡型。** 普通固定 UID 卡也可能通过 CUID 模式的认证/读取检查，但会拒绝实际写入。写入成功也只能证明本次标准写入及回读成功，不能证明它可反复写或一定是 CUID；部分一次性 / OTP 卡可能因此锁定。准备过程不会发送写入命令，包括“写回原值”或只发 WRITE 前导。

`PICC_HaltA()` 是休眠，不是卡片复位。本程序切换写入方式前先停止 Crypto1，关闭/重开射频场，再重新寻卡和认证。用户确认后如果目标或已选写法检查失败，程序会停止，不会自动切换其他写法继续写。

备份必须含兼容的第 0 块：前 4 字节等于备份 UID，第 5 字节是这 4 字节的异或校验（BCC），后面的 SAK / ATQA 字节为 `08 04 00`。布局不符会停止，避免将不兼容的厂家信息写进 Gen1A 卡。你提供的备份符合这个布局：

```text
原卡 UID：AB0A1EBB
第 0 块：AB0A1EBB0408040003C234747F4CA890
```

网页操作：

1. 先按普通流程恢复并校验 47 块用户数据。你已经取得 `VERIFY OK: 47/47`，可以直接进行下一步。
2. 移走原卡，**读卡器附近只放一张目标卡**。Gen1A 特殊指令不依赖普通选卡过程，因此不能同时放着两张卡。
3. 在网页下方选择“自动选择”，点击“检查第 0 块写入”。也可明确选择仅 UID 或仅 CUID。此时只检查、读取，没有写入。
4. 页面显示本次写法、目标当前 UID、写入后的 UID 和待写入的完整 16 字节。例如 `9EBA0902 → AB0A1EBB`。若进入 CUID 标准方式，页面会强调“尚未验证可写”和一次性卡的限制。
5. 在 30 秒倒计时内点击对应的确认按钮，保持目标卡不动、供电稳定。两种确认独立绑定目标卡号、备份和本次确认码，不能混用。
6. 成功时页面会明确显示“第 0 块写入成功”，串口显示 `BLOCK0 OK`。程序已经断开并重开射频、重新识别新 UID，且用普通认证读取第 0 块确认全部 16 字节一致。
7. 点击“识别卡片”可再次确认实际卡号已变为 `AB0A1EBB`；“校验目标卡”仍可检查 47 个用户数据块。

**先恢复 47 块，最后写第 0 块。** 改完 UID 后，目标卡与原卡卡号相同，程序无法仅凭卡号区分两者；普通恢复会按原卡保护规则拒绝再次写入。识别和用户数据校验仍可使用。

这会覆盖整个厂家块，不只是 UID 的 4 字节。如果写入 ACK、重新识别或回读失败，程序会报告 `BLOCK0 UNCONFIRMED`：卡片可能已经修改，不能视为成功，也不会自动重试或回滚。检查步骤未通过时则不会发出任何写入指令。

串口也可操作。发送：

```text
prepare-auto
```

程序检查后会打印独立确认命令，例如：

```text
WRITECUID 9EBA0902 12
```

这是自动选择标准写法后的示例；若检查确认 Gen1A 方式，则会打印 `WRITE0 9EBA0902 12`。最后的 `12` 是本次确认码，仅为示例，必须原样发送设备实际打印的整行。`WRITECUID`、`WRITE0`、普通 `WRITE` 三种确认不通用，确认码、目标卡号、原始第 0 块或源备份变化都会使检查失效。超时后重新检查。`prepare-block0` 保留为仅 Gen1A 检查；`prepare-cuid` 为仅普通认证准备。

不要对新卡执行 `backup` 来确认卡号，那会把原卡备份替换掉；识别卡号用 `info` 即可。若标准写入返回 NAK，程序只说明卡片拒绝，不认定厂家或正品身份；认证失败、读取失败和写入失败会分别报告。

“下载已保存的备份”和 `dump` 始终导出 ESP32 中保存的原卡数据，不会实时读取天线上的卡。网页的“最近读取的卡片”才显示最近一次识别结果。

### 分阶段诊断

本版提供 Gen1A 与标准认证写入的诊断日志。未增加 Gen1B 等其他特殊协议。

放上目标卡后，发送 `prepare-auto`，或者在网页选择方式后点击“检查第 0 块写入”。网页可以展开“查看最近操作的详细诊断”，选中文字复制；串口同时输出各阶段结果。检查阶段不发送任何写入指令。

| 日志阶段 | 检查内容 |
| --- | --- |
| `SOURCE0` | 板上源备份完整性与第 0 块布局 |
| `AUTH0` | 使用已配置 Key A 对目标第 0 扇区认证 |
| `READ0/AUTHENTICATED` | 普通认证后读取目标第 0 块，显示 16 字节 |
| `TARGET0/UID-BCC` | 第 0 块中的 UID/BCC 与实际识别结果是否匹配 |
| `GEN1A/HANDSHAKE` | 现有库的 Gen1A 握手是否完成 |
| `READ0/GEN1A` | 特殊模式下读取第 0 块是否成功 |
| `COMPARE0/GEN1A` | 两次读到的完整 16 字节是否一致 |
| `RF/CLEANUP` | 检查结束后关闭特殊会话 |
| `STANDARD/FALLBACK` | Gen1A 未通过后，重启射频场并重新选择目标 |
| `STANDARD/ACCESS` | 普通认证后的访问位检查，不能证明厂家块可写 |
| `STANDARD/PREPARED` | 仅完成读取检查，卡型与可写性仍未确认 |
| `STANDARD/WRITE0` | 已得到明确确认，即将执行一次实际标准写入 |
| `WRITE0/METHOD` | 本次写法已经通过新 UID 和完整第 0 块回读验证 |

库内详细串口日志已经启用。若握手失败，串口会说明是在 `0x40` 还是 `0x43` 阶段超时或响应异常；网页会标识握手失败并提示查看串口。后续读取失败则会显示读取状态码，内容不一致会列出期望值与实际值。不能仅凭某一握手阶段失败判定卡片型号。

只保留最近一次操作的诊断；故障后先复制日志，再发其他命令。日志最大 4096 字符，正常单次流程不会超过该长度。实际写入流程还会记录 `WRITE0/ACK`、`VERIFY/UID` 和 `VERIFY/BLOCK0`；写后完整校验规则保持原样。

## 1. 硬件与支持范围

照片中的读卡模块是 RC522 常见的 8 针 SPI 接口板，丝印为 `SDA SCK MOSI MISO IRQ GND RST 3V3`，并有 `MH-ET LIVE V2.0` 标识。“RC552”通常是“RC522”的笔误；芯片版本可在烧录后查看。开发板是带两个 Type-C 接口的 ESP32-S3 类开发板，可使用 `ESP32S3 Dev Module` 通用配置。

| 卡片 | 本程序支持情况 |
| --- | --- |
| MIFARE Classic 1K / M1 / S50，4 或 7 字节 UID | 识别；已知对应扇区密钥时读取用户数据 |
| 新的 M1 / S50 卡，出厂 Key A 与访问位 | 恢复 47 个用户数据块，并逐块校验 |
| 兼容 Gen1A 的 4 字节 UID S50 卡，第 0 扇区默认 Key A | 在独立确认后复制整个第 0 块；普通恢复仍只写 47 块 |
| 支持标准写入第 0 块的 CUID / Gen2 类 4 字节 UID S50 卡 | 默认 Key A 与出厂访问位检查后，独立确认并尝试一次写入；不将准备成功当作可写性证明 |
| MIFARE Classic 4K / Mini | 可报告识别类型；本版本不备份、不写入 |
| NTAG / Ultralight | 可报告识别类型；本版本不备份、不写入 |
| DESFire / CPU 卡、公交卡等 | 有的可读到 UID / 类型，但不支持本程序的数据备份流程 |
| 125 kHz ID 卡 | RC522 硬件不支持 |

识别结果根据卡片返回的 SAK 推断，不能据此证明卡片芯片真伪或可复制性。RC522 是读写器，不能让 ESP32 + RC522 直接模拟一张卡。

## 2. 接线：7 根杜邦线

**先断开 USB 电源再接线。RC522 的 3V3 必须接开发板的 3V3，不能接 5V。** 接线按板上丝印的 GPIO 数字，不能按排针第几脚来数。

| RC522 丝印 | ESP32-S3 丝印 | 作用 |
| --- | --- | --- |
| `3V3` | `3V3` | 3.3V 供电 |
| `GND` | 任一 `GND` | 共地 |
| `SDA` | `10` / GPIO10 | SPI 片选 CS / SS |
| `SCK` | `12` / GPIO12 | SPI 时钟 |
| `MOSI` | `11` / GPIO11 | 主控发送 |
| `MISO` | `13` / GPIO13 | 主控接收 |
| `RST` | `14` / GPIO14 | 读卡器复位 |
| `IRQ` | 不接 | 本程序不使用中断 |

两个容易接错的地方：RC522 的 `SDA` 在此处是 SPI 片选，不是 I²C SDA；RC522 的 `RST` 接 **GPIO14**，不是开发板的 `RST` 引脚。杜邦线尽量短，例如 10～15 cm，避免松动。

代码对应 `SPI.begin(12, 13, 11, 10)`，顺序是 SCK、MISO、MOSI、SS。引脚配置集中在 [Config.h](CardBackup/Config.h)。

## 3. 用 Arduino IDE 烧录

1. 安装 [Arduino IDE 2](https://www.arduino.cc/en/software)。需要一条**能传数据**的 USB Type-C 线。
2. 在设置里的“附加开发板管理器网址”添加：

   ```text
   https://espressif.github.io/arduino-esp32/package_esp32_index.json
   ```

   若官方下载困难，可按[乐鑫安装文档](https://docs.espressif.com/projects/arduino-esp32/en/latest/installing.html)使用其列出的中国镜像。
3. 打开“开发板管理器”，安装 **esp32 by Espressif Systems**，使用稳定版 3.x。
4. 打开“库管理器”，安装 **MFRC522 by GithubCommunity，1.4.12**。`SPI`、`Preferences`、`WiFi`、`WebServer` 和 `DNSServer` 已随 ESP32 开发板包提供，无需另装。
5. 用“文件 → 打开”打开 [CardBackup/CardBackup.ino](CardBackup/CardBackup.ino)。保留同一文件夹里的所有 `.h`、`.cpp` 文件，不要只复制 `.ino` 文件。
6. 选择开发板 **ESP32S3 Dev Module**，按下面配置并选中插板后新增的端口。

| Arduino 工具菜单 | 配置 |
| --- | --- |
| Board | `ESP32S3 Dev Module` |
| CPU Frequency | 默认 `240MHz` |
| Flash Mode | `QIO 80MHz`；不能启动时检查实际模块规格 |
| Flash Size | 若模块丝印为 `N16R8` 则选 `16MB (128Mb)`；否则按实际容量 |
| Partition Scheme | `Default 4MB with spiffs` 即可，也能用于 16MB Flash，只使用其中一部分 |
| PSRAM | `Disabled`，这个程序不需要 PSRAM |
| Upload Speed | 先选 `115200` |
| Upload Mode | `UART0 / Hardware CDC` |
| USB Mode | `Hardware CDC and JTAG` |
| USB CDC On Boot | 取决于使用哪个 USB 口，见下一表 |
| Erase All Flash Before Sketch Upload | `Disabled`，以免删除已保存的卡片备份 |

### 两个 Type-C 口怎样选

照片不足以可靠确认两个插口的功能丝印，因此不按“左边/右边”猜。查看板上 `USB` / `UART` 标识或卖家原理图，**先只连接一个 USB 口**。

| 使用的接口 | `USB CDC On Boot` | 串口监视器使用的端口 |
| --- | --- | --- |
| ESP32-S3 原生 USB，通常标 `USB` / `OTG` | `Enabled` | ESP32 USB CDC 端口；Mac 上常见 `/dev/cu.usbmodem…` |
| USB 转串口芯片接口，通常标 `UART` / `COM` | `Disabled` | 对应的 CH34x / CP210x 等串口；Mac 上常见 `/dev/cu.usbserial…`、`/dev/cu.wchusbserial…` |

端口名只是辅助判断，并不是绝对依据。使用 UART 口但开启 CDC 时，烧录可能成功，程序日志却输出到另一个 USB 口。如果转串口接口未出现设备，按实际芯片型号安装厂家驱动。

7. 点击“验证”编译，再点击“上传”。若一直停在 `Connecting...`：按住 **BOOT**，按一下并松开 **RST**，再松开 BOOT；选择出现的下载端口后重新上传。
8. 上传结束后按一下 **RST**。原生 USB 的运行端口可能重新枚举，需要重新选择端口。
9. 打开“串口监视器”，波特率 **115200**，行结束符选 **Newline / 换行符**，或 **Both NL & CR**。输入 `help` 并发送。

手机操作见本文开头的快速使用步骤。以下章节保留串口操作说明，方便调试；串口和网页使用同一份备份和同一套读写检查。若没有及时看到串口启动日志，发送 `help`、`status` 即可。

## 4. 第一次使用：先只识别、备份

读卡时把**一张**卡贴近模块天线区域，保持稳定。每次等卡最多 15 秒；命令可在放卡后发送，也可发送后再放卡。

### 第一步：识别原卡

在串口发送：

```text
info
```

可能看到：

```text
UID: A1B2C3D4
UID bytes: 4, SAK: 08
Type (inferred from SAK): MIFARE 1KB
```

这表示适合继续尝试本程序的备份流程，**不表示已经读出了数据或密钥**。没有其他命令时，程序不会自动写卡。

### 第二步：备份原卡

保持原卡贴在天线上，发送：

```text
backup
```

默认使用每个扇区的出厂 Key A：`FF FF FF FF FF FF`。全部读取成功才保存，并输出 `BACKUP OK`。任何扇区认证/读取失败都中止，保留原有备份，不会用缺失内容覆盖旧备份。

保存内容：47 个用户数据块，共 752 字节；原卡 UID、SAK；第 0 块元数据。第 0 块默认仅保存，在独立 UID / CUID 流程下可写入兼容目标卡。所有 16 个扇区尾块均不保存；它们包含密钥与访问控制数据，不能把读回值当成完整密钥备份。

ESP32 的 NVS Flash 只保存**最近一份成功备份**，重启、断电后仍保留。再次成功执行 `backup` 会替换它。清空 Flash、更改分区布局或发送 `erase-backup` 都可能删除备份。

### 第三步：查看、导出

分别发送：

```text
status
dump
```

`dump` 输出 JSON，可复制从 `{` 到 `}` 的内容保存为电脑文件。它明确标记为用户数据备份，不是完整 1KB 原始镜像。**本版本没有 JSON 导入命令**；恢复使用板上 NVS 中的备份，因此先保留板上数据。

### 如果认证失败

例如 `ERROR: authenticate, block 7` 对应第 1 扇区认证失败。可能是该扇区不是默认密钥，也可能是距离或通信不稳定。确认读卡稳定后，只有掌握真实密钥才能读取受保护的数据。

在 [Config.h](CardBackup/Config.h) 中，将 `SOURCE_KEYS[扇区号]` 对应那一行改为已知的 6 字节密钥；如果用 Key B，将相应 `SOURCE_USE_KEY_B` 元素改为 `true`。重新编译烧录时保持相同分区、不要全片擦除。程序只尝试你配置的一个密钥，不运行字典或破解算法。

## 5. 可选：恢复到另一张空白 M1 卡

只有拿到明确可覆盖的 M1 / S50 空白卡时才执行；先把原卡移开。目标需要每个扇区的 Key A 为 `FFFFFFFFFFFF`、访问位为出厂配置 `FF0780`。程序会先检查全部 16 个扇区。

1. 放目标空白卡，发送 `restore`。
2. 程序显示目标 UID，例如 `11223344`，并要求在 30 秒内发送：

   ```text
   WRITE 11223344
   ```

   使用程序实际显示的卡号，保留大写 `WRITE` 与大写十六进制；不要照抄示例卡号。
3. 保持同一张目标卡不动，发送该确认行。程序重新核对卡号、排除原卡，并再次检查全部扇区，然后写入 47 个用户数据块，每写一块立即回读校验。
4. 输出 `RESTORE OK` 后，再发送 `verify` 可重新读完整的 47 块进行比较。

超时、换卡、输入其他命令、发送 `cancel` 都会取消待写状态。目标 UID 与原卡 UID 相同会被拒绝，因此本版本也不会写入已改成原卡 UID 的特殊卡。

**普通恢复不修改第 0 块和第 3、7、11……63 块，不复制 UID、密钥和访问权限。** 需要复制卡号时，在此流程之后使用本文开头的独立 UID / CUID 第 0 块流程。普通固定 UID 的 M1 卡不会因为知道扇区密钥而解除厂家块只读限制。

写卡不是原子操作。途中拔卡、断电或通信失败，目标可能只写了一部分，程序会报告已验证的块数，不会显示成功，也没有自动回滚。板上的源数据备份仍可用于重新恢复。

## 6. 命令速查

| 命令 | 作用 |
| --- | --- |
| `help` | 显示帮助 |
| `info` | 只读识别当前卡 |
| `backup` | 读取原卡，成功后覆盖板上备份 |
| `status` | 显示备份 UID、CRC 等 |
| `dump` | 串口导出用户数据 JSON |
| `restore` | 检查空白目标卡，等待确认 |
| `WRITE 实际卡号` | 确认写入已准备好的目标卡 |
| `prepare-block0` | 对新卡做 Gen1A / 第 0 块只读检查，准备独立确认 |
| `prepare-auto` | Gen1A 读取验证优先，失败后做标准认证读取准备，显示待尝试的写法 |
| `prepare-cuid` | 仅做普通认证读取与访问位检查，不检测实际可写性 |
| `WRITE0 实际卡号 确认码` | 按实际打印的命令，确认写入第 0 块并验证新 UID / 16 字节 |
| `WRITECUID 实际卡号 确认码` | 按实际打印的命令，确认尝试一次标准认证写入，并验证新 UID / 16 字节 |
| `verify` | 用默认 Key A 比较目标卡的 47 个数据块 |
| `cancel` | 取消待确认写入 |
| `erase-backup` | 删除 ESP32 中的备份，不写卡 |

## 7. 故障排查

| 现象 | 优先检查 |
| --- | --- |
| 找不到热点 | 等待开机几秒，检查供电和串口 `Wi-Fi hotspot:` 输出；手机需要支持 2.4 GHz Wi-Fi |
| 已连热点，网页打不开 | 输入 `http://192.168.4.1`；手机选择继续连接无互联网网络，检查 VPN 和自动网络切换 |
| 页面显示连接断开 | 操作按钮会禁用；先恢复热点连接，页面会自动同步实际状态，不会自动重发写卡请求 |
| 确认已过期 | 再次点击“检查目标卡”，核对卡号后在倒计时结束前确认 |
| `BLOCK0 UNSUPPORTED` | 新卡未通过 Gen1A 检测或通信不稳定；没有写卡，核对卡型及位置 |
| `BLOCK0 REFUSED` | 备份布局、目标卡号、完整第 0 块或确认信息不符合要求；没有写卡 |
| `BLOCK0 UNCONFIRMED` | 已尝试写入，但结果未确认；卡片可能已修改，先重新识别和排查，不视作成功 |
| 串口无输出 | USB 线能否传数据、端口选择、CDC 设置是否与接口对应；发 `help` |
| `VersionReg` 为 `0x00` 或 `0xFF` | 3.3V、共地、MISO/MOSI 是否接反、SDA 是否接 GPIO10、RST 是否接 GPIO14 |
| 版本为 `0x91` / `0x92` | 常见 MFRC522 版本，但仍需实际刷卡确认通信；兼容芯片可能显示其他值 |
| 检测到模块但无卡 | 贴近天线、一次一张、远离金属；确认不是 125 kHz ID 卡 |
| 可读 UID，但认证失败 | 数据区密钥/权限与默认值不同，或通信不稳定；UID 可读不代表数据可读 |
| `Type` 不是 `MIFARE 1KB` | 暂停备份/恢复，用识别结果确定下一步方案 |
| `Preflight failed` | 目标不是出厂配置或通信异常；程序尚未写入 |
| `STOPPED` | 目标可能部分写入；稳定供电和位置后重新执行 `restore` |
| `VERIFY OK` 但设备不认新卡 | 数据一致不等于 UID、密钥、权限和后台状态一致 |

## 8. 验证与参考资料

本工程使用 **Arduino-ESP32 3.3.11 + MFRC522 1.4.12**，默认 4MB 分区，PSRAM 关闭，原生 USB CDC 开启。原普通流程已根据你的实机日志验证识别、备份、恢复和 47 块校验。UID / CUID 第 0 块流程需要烧录后验证真实卡片的兼容性和射频读写；模拟测试不能证明你手里的新卡一定支持改写 UID。

UID / CUID 双模式版通过 ESP32-S3 实际编译：程序 981,101 字节（74%），全局变量 47,624 字节（14%）。默认 4MB 分区可容纳程序，不需要更改原分区或开启全片擦除。

编译命令（已安装 Arduino CLI 和相关开发板/库时）：

```sh
arduino-cli compile --fqbn 'esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,FlashSize=4M,PartitionScheme=default,PSRAM=disabled' CardBackup
```

完整主机测试可运行（首次需要联网下载两个已固定版本的接口头文件）：

```sh
sh tests/run_host_tests.sh
```

其中不需要联网的备份格式测试也可单独运行：

```sh
c++ -std=c++11 -Wall -Wextra -Werror tests/backup_format_test.cpp -o /tmp/iccard-format-test
/tmp/iccard-format-test
```

格式测试验证 CRC 标准向量、8,384 种单比特损坏的检出、写入地址范围（排除 UID 和尾块）、UID 比较与目标访问位判断。流程模拟另外覆盖：重启加载备份、部分读取失败保留旧数据、拒绝写原卡、取消/超时/换卡、写前权限检查、47 块写入与回读、保护块内容不变、写失败/校验失败中止、未知卡型和损坏的 NVS 备份。

新增的主机测试覆盖网页命令排队、重复请求拒绝、旧确认失效、读写中的操作互斥、状态轮询不取消确认、到期处理与 JSON 导出。模拟环境见 `tests/host`，不模拟真实射频与电气行为。

第 0 块测试进一步覆盖兼容布局、UID/BCC/SAK/ATQA 拒绝条件、普通卡探测拒绝、特殊会话关闭、换卡与厂家块变化、源备份变化、两种确认隔离、过期/旧确认码、单次 16 字节写入、重新选卡及普通认证回读、写入失败与结果不一致，确保这些失败不会报告成功。

标准认证与自动选择测试覆盖：准备阶段零次写入、失败后重启射频并重选同卡、普通卡 NAK、普通认证会话保持到写入、只改第 0 块、三种确认隔离、过期/旧确认/重复请求、写后完整校验，以及确认后的失败不自动重试或换写法。

页面脚本测试（Node.js 18+）覆盖状态显示、重复点击、目标确认、倒计时、备份替换/删除弹窗、下载和断线恢复：

```sh
node tests/web_ui_test.mjs
```

本版已在浏览器中用模拟 CUID 卡验证自动检查、标准写入确认、30 秒确认过期及模拟成功后的新 UID 显示。页面脚本测试另覆盖三种方式选择、确认路由隔离及诊断文本显示。浏览器预览使用模拟后台，实际手机 Wi-Fi 与卡片射频行为仍需上板确认。

本机页面预览使用可丢弃的模拟卡片，不连接实物：

```sh
python3 tests/web_preview.py --card-type cuid
```

在浏览器打开 `http://127.0.0.1:8765` 可检查交互；`--card-type` 可选 `gen1a`、`cuid`、`fixed`（模拟标准写入被拒绝）。真实设备使用 `http://192.168.4.1`。预览页顶部明确标记模拟环境。
